# SQLite KV

Wabou includes an opt-in hierarchical key-value service for small durable
application records. The native store uses embedded SQLite through
`wabou-database`; JavaScript receives typed structured
values through the ordinary native capability boundary.

Enable it together with a stable application identity:

```rust
HostBuilder::new()
    .app_directories("com", "Example", "Workbench")
    .kv()
    .run()?;
```

The default database is stored below the platform-local application data
directory at `storage/kv/default.sqlite3`. Behavior tests inherit Wabou's
isolated application-data root and therefore cannot modify real user data.

## Hierarchical keys

Keys are arrays rather than delimiter-separated strings. This makes namespace
boundaries explicit and avoids escaping bugs:

```ts
import { openKv } from "@wabou/core";

const settings = openKv(["settings"]);
await settings.set(["theme"], { mode: "light" });

const projects = openKv(["projects", projectId]);
await projects.set(["draft"], { text: "hello" });

for await (const entry of projects.list({ prefix: ["sessions"] })) {
  console.log(entry.key, entry.value);
}
```

JavaScript key parts may be strings, safe integers, booleans, or
`Uint8Array`s. Values are JSON-compatible structured values. Large images and
files belong in Wabou's resource/file systems; store their handles or metadata
in KV instead of copying their bytes into SQLite.

## Versions and atomic commits

Every successful commit receives a decimal `versionstamp`. It is generated by
the database, is safe to carry through JavaScript without numeric precision
loss, and supports optimistic concurrency:

```ts
const kv = openKv(["documents"]);
const current = await kv.get([documentId]);

const result = await kv
  .atomic()
  .check({
    key: [documentId],
    versionstamp: current?.versionstamp ?? null,
  })
  .set([documentId], { text: "updated" })
  .commit();

if (!result.committed) {
  // Another writer changed the document. Reload and resolve the conflict.
}
```

All checks run inside the same SQLite transaction as all mutations. A `null`
versionstamp checks that a key is absent; expired records also count as absent.
Multiple `set` operations in one atomic commit share one versionstamp.

`versionstamp` is data revision metadata, not application schema versioning.
The KV table schema is migrated internally by Wabou. Domain migrations should
use explicit application keys (for example `["meta", "schemaVersion"]`) and an
atomic migration appropriate to that application's data.

## Expiration

`set` accepts a relative expiration duration in milliseconds:

```ts
await kv.set(["transient", requestId], payload, { expireIn: 60_000 });
```

Expired records are immediately treated as absent by reads, lists, and atomic
checks. Physical cleanup is an implementation detail and does not affect the
observable API.

## Solid state

`createKvSignal` provides immediate local state, asynchronous hydration,
coalesced writes, and a cleanup flush. Its key is mandatory so persistence
does not depend on signal creation order or source locations:

```ts
import { createKvSignal, openKv } from "@wabou/core";

const theme = createKvSignal({
  kv: openKv(["settings"]),
  key: ["theme"],
  initial: { mode: "light" },
});

theme.set({ mode: "dark" });
await theme.flush();
```

An edit made before hydration finishes wins over the older durable value. Load
and write failures are exposed through `error()` instead of silently reverting
the local signal.

## Rust access

Applications that need the same semantics without JavaScript can use the
facade exports `KvStore`, `KvKeyPart`, `KvMutation`, and `KvCheck`. Open a
separate KV database file rather than combining it with an application-owned
`Database`: each database owns its own SQLite migration version.

The first release deliberately omits Dexie-style secondary indexes and live
queries. Structured domain data that needs joins or indexed predicates should
use `wabou-database` and application-owned SQL tables. Prefix lookup,
versionstamps, expiration, and atomic compare-and-set cover the intended KV
use cases without turning the API into a second relational query language.
